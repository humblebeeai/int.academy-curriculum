# 🌐 Systems & Networking

![Placeholder: Banner Image for Networking - TCP/IP and Servers]

> **"If you don't understand TCP/IP, you can't build distributed systems."**

## Overview

**Duration**: 1-2 weeks | **Prerequisites**: Module 1 (Computational Thinking) completed

This module reveals how computers communicate across the internet. Understanding networking is essential for deploying AI models, debugging connection issues, and building secure, scalable systems. You'll learn the foundational concepts that power every API call, model deployment, and distributed application.

**Learning Outcomes:**
- Explain how data travels from your computer to servers and back
- Understand IP addressing, subnetting, and network segmentation
- Configure secure port mappings for deployed applications
- Troubleshoot network issues when deploying AI models
- Design secure network architectures for production systems

**Why This Matters for AI:**  
When you deploy a model, it runs on a server with an IP address, listening on specific ports. Clients access it through network requests. Without understanding subnetting, firewalls, and port forwarding, you cannot deploy secure, accessible APIs or debug why "it works locally but not in production."

### Module 2: Network Models & Protocols

#### 2.1 The OSI & TCP/IP Models

**Resource**: [TCP/IP vs. OSI Models (NetworkChuck)](https://youtu.be/CRdL1PcherM?si=iHWLHjJ9f0xprSrV)  
**Type**: Video | **Duration**: 18 minutes

**Why This Resource**  
These models are the mental framework for understanding how networks actually work. Every networking conversation references these layers.

**What You'll Learn**
- OSI 7-layer model (Physical → Application)
- TCP/IP 4-layer model (more practical)
- What happens at each layer when you request a webpage
- How protocols at different layers work together
- Troubleshooting using the layer model

**How to Use**
1. **Critical**: Create a reference chart of both models side-by-side
2. For each layer, write one real-world example
3. **Practice checkpoint**: Identify which layer handles:
   - Ethernet cables (Physical - Layer 1)
   - IP addresses (Network - Layer 3)
   - HTTP requests (Application - Layer 7)
4. Memorize at least the TCP/IP model layers

**The Layers (TCP/IP Model)**
1. **Link Layer**: Hardware addressing (Ethernet, WiFi)
2. **Internet Layer**: Routing across networks (IP)
3. **Transport Layer**: Reliable delivery (TCP) or fast delivery (UDP)
4. **Application Layer**: Your code (HTTP, HTTPS, SSH, FTP)

**Why This Matters**  
When debugging, you can isolate problems: "Is this a Layer 3 routing issue or a Layer 7 application error?"

## Practical Integration Project

### Project: Secure AI Model Deployment Architecture

**Duration**: 4-6 hours

Design and document a network architecture for a production AI system.

**Requirements:**
1. **Network Diagram** showing:
   - Public subnet (load balancer)
   - Private subnet (API servers)
   - Private subnet (database)
   - CIDR blocks for each subnet

2. **Security Configuration**:
   - Which ports are open on each component
   - Firewall rules (who can talk to whom)
   - Public vs private IP assignments

3. **Traffic Flow Documentation**:
   - User request → Load balancer → API → Database
   - Show which layer of TCP/IP handles each step

**Example Architecture**:
```
Public Subnet (10.0.1.0/24)
- Load Balancer: 10.0.1.10
- Ports: 80 (HTTP), 443 (HTTPS)

Private Subnet - App Tier (10.0.2.0/24)
- FastAPI Server 1: 10.0.2.10:8000
- FastAPI Server 2: 10.0.2.11:8000
- No external access (only from load balancer)

Private Subnet - Data Tier (10.0.3.0/24)
- PostgreSQL: 10.0.3.10:5432
- Redis: 10.0.3.11:6379
- No external access (only from app tier)
```

**Verification Checklist**
- [ ] Subnets are properly sized (not too many wasted IPs)
- [ ] No database ports exposed to internet
- [ ] Load balancer can reach all app servers
- [ ] App servers can reach database
- [ ] Users can only access load balancer (port 80/443)

## Common Pitfalls & Troubleshooting

**Understanding Issues**
- ⚠️ **Confusing switches and routers**
  - ✅ Switches connect devices in the same network (Layer 2), routers connect different networks (Layer 3)

- ⚠️ **Forgetting which layer does what**
  - ✅ Keep a reference chart: Physical cables → Data link (MAC) → Network (IP) → Transport (TCP/UDP) → Application (HTTP)

**Practical Issues**
- ⚠️ **"My API works locally but not after deploying"**
  - ✅ Check: Firewall blocking port? Listening on 0.0.0.0 not 127.0.0.1? Security group rules?

- ⚠️ **"Database connection refused"**
  - ✅ Check: Port 5432/3306/27017 open? Database on same network? Connection string has correct IP?

- ⚠️ **"Slow API responses"**
  - ✅ Check: Network latency (use `ping`), TCP connection overhead, geographic distance

**Security Mistakes**
- ⚠️ **Exposing database ports to internet**
  - ✅ Databases should only accept connections from application servers (private subnet)

- ⚠️ **Using default ports without firewall**
  - ✅ Change default ports or restrict access with firewall rules

## Real-World Networking Scenarios

### Scenario 1: Deploying to AWS
**Problem**: You've deployed your FastAPI to EC2, but can't access it.

**Debugging Steps**:
1. Check security group (AWS firewall): Is port 8000 open?
2. Verify app is listening on 0.0.0.0 not 127.0.0.1: `netstat -tlnp | grep 8000`
3. Test from EC2 itself: `curl localhost:8000` works? → Firewall issue
4. Check route table: Is subnet's traffic routed to internet gateway?

---

### Scenario 2: Database Won't Connect
**Problem**: Your app can't reach PostgreSQL.

**Debugging Steps**:
1. Layer 1: Physical connection exists? (Cloud: instances in same VPC?)
2. Layer 3: Can you ping the database server? If not, routing issue
3. Layer 4: Is PostgreSQL listening on 5432? `netstat -tlnp | grep 5432`
4. Layer 4: Is port 5432 open in firewall? `telnet db-server 5432`
5. Layer 7: Check connection string (correct host, user, password)

---

### Scenario 3: Designing Multi-Region Architecture
**Problem**: Users in Asia experience slow API responses (you're in US).

**Solution Using Networking Concepts**:
1. Deploy API servers in Asia region (reduce latency)
2. Use GeoDNS to route users to nearest server
3. Implement CDN for static assets (Layer 7 optimization)
4. Use database replication across regions
5. Monitor with `traceroute` to verify path optimization

## Quick Reference

**Private IP Ranges** (memorize these)
```
10.0.0.0    - 10.255.255.255   (10.0.0.0/8)
172.16.0.0  - 172.31.255.255   (172.16.0.0/12)
192.168.0.0 - 192.168.255.255  (192.168.0.0/16)
```

**Common Port Numbers**
```
SSH:        22
HTTP:       80
HTTPS:      443
PostgreSQL: 5432
MySQL:      3306
MongoDB:    27017
Redis:      6379
FastAPI:    8000 (development)
```

**TCP/IP Layers**
```
4. Application  → HTTP, HTTPS, SSH, FTP
3. Transport    → TCP (reliable), UDP (fast)
2. Internet     → IP routing
1. Link         → Ethernet, WiFi
```

**Essential Commands**
```bash
# Test connectivity
ping google.com

# Show route to destination
traceroute google.com  # Linux/Mac
tracert google.com     # Windows

# View open ports
netstat -tuln          # Linux
netstat -an            # Windows

# Find your IPs
ip addr                # Linux
ipconfig               # Windows
ifconfig               # Mac

# Test specific port
telnet server-ip 8000
nc -zv server-ip 8000  # netcat alternative
```

Save this reference for quick lookup during deployment and debugging.
